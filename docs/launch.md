# Guided free pilot and future scaling

This pilot uses Render's free web service and Neon Free PostgreSQL. Select Free in both providers. Do not enable paid workspace features, paid compute, or automatic upgrades during setup. Free tiers have quotas and Render sleeps when inactive; this plan does not promise always-on service or automatic horizontal scaling. Check the provider's current plan screen before creating resources.

1. Sign into Render and Neon with your GitHub account. In Neon, create a Free project in Frankfurt, PostgreSQL 17 or 18, with database `nabeeh`. Create a separate branch for development/test work if needed; do not run the repository's destructive test fixtures against the production database.
2. Review the GitHub `nabeeh-launch` branch, then connect that repository in Render. Select **New → Blueprint**, choose the repository and `nabeeh-launch` branch, and review render.yaml. It creates only the Free web service; the database is external. You can deploy this branch directly and merge it into main after reviewing the pilot.
3. Neon **Connect** provides the connection string. Turn **Connection pooling** on, copy the pooled URI, and paste it into Render's secret environment variable **DATABASE_URL**. Keep the provider's TLS parameters. Do not paste the URI in chat, issues, screenshots, or repository files. Optionally add **DATABASE_MIGRATION_URL** with the direct URI for deployment migrations. The existing migration advisory locks are transaction-scoped and work through transaction pooling.
4. Render uses the repository Dockerfile. Its default command runs migrations, installs the release drafts idempotently, optionally provisions an operator-specified administrator, and starts the server. Use `/health` as the health check. `RENDER_EXTERNAL_URL` supplies the canonical HTTPS origin; if adding a custom domain, set `APP_ORIGIN=https://your-domain` explicitly. Secure cookies are mandatory.
5. Open Render's HTTPS service URL. Create your own account and save the private recovery key. Then set **ADMIN_USERNAME** in Render to your exact registered username and redeploy. The trusted startup command grants that existing account admin without needing your password. Remove ADMIN_USERNAME after the grant. Do not set an unknown user's name. No public endpoint grants roles.
6. Sign back in, open **غرفة التحرير**, and review each draft. Media previews, answers, proofs and similarity candidates are shown to editors. Enter a meaningful review note, check the similarity-review checkbox where needed, and approve individually. The 36 initial drafts appear in docs/release-review.md; none were auto-approved. The older 48 development questions require exact-source review and remain excluded from production.
7. Play a complete game, reveal/score questions, refresh mid-game, sign in from a second browser, and confirm resume/no-repeat behavior. Send the public service URL so these checks can also be made externally. A successful local build does not establish that the hosted deployment works.

The pilot worker runs inside the web service (`RUN_WORKER=true`), avoiding a paid background-worker resource. It resumes durable queued jobs when the service runs. Free-service suspension can interrupt work; leases/retries preserve jobs, but continuous unattended generation requires an always-on worker. No MODEL_API_KEY is included, and the pilot's model-generation budget is zero. Original proposals still need editor approval.

## When usage grows

Keep the application and database close geographically. Add a managed Redis service, set REDIS_URL with verified TLS, and set REQUIRE_SHARED_LIMITS=true **before** increasing the app's replica count. Redis failure closes the rate-limit gate rather than bypassing it. TRUST_PROXY_HOPS=1 assumes requests go through Render's single public edge proxy; review that topology again if adding another proxy/CDN.

On paid Render plans, move the worker to a separate worker service (`RUN_WORKER=false` on the web service). Pro workspace autoscaling can change instance count between chosen bounds. Start with measured bounds, not unlimited growth. Set database connection budgets across all app and worker processes: `replicas × DB_POOL_MAX + workers × DB_POOL_MAX` must stay within your chosen pooler's backend capacity, with room for migrations/operator connections.

Enable Neon's database autoscaling within an explicit compute range and monitor connection count, query latency, memory, storage, and cost. Media uploads use an S3-compatible private object store configured through MEDIA_BUCKET, MEDIA_ENDPOINT, MEDIA_REGION, MEDIA_ACCESS_KEY_ID and MEDIA_SECRET_ACCESS_KEY. Bundled original pilot assets require no external storage account and remain identical across replicas.

Game selection uses indexed UUID rotation with exact transactional exclusions, not a full random sort. Lexical retrieval uses pg_trgm, and the optional 1536-dimensional semantic index uses pgvector HNSW when the database supplies the extension. Live model quality and embedding recall must be evaluated before relying on them editorially. Scores, reservations and exposure decisions use the primary database; offload suitable analytics to read replicas.

Use database recovery/PITR appropriate to the plan, perform a restore drill in an isolated database, and monitor `/health`, failures, job backlog and approved inventory. Recovery codes are single-use and valid for one year; there is no email reset until a verified email/OIDC service is configured. Decide support contact, terms, privacy and retention before opening registration broadly. Account deletion and export already exist.
